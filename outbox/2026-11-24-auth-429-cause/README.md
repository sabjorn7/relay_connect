# Причина задержки восстановления после конкурентного refresh

Основа: ca9bb1f. Только локальная диагностика в `/private/tmp/mg-auth-429-20261124/candidate`. Product-код, SDK, сериализация, cookies, production и CI не изменены. SDK-diff ниже только предложен, не применён; дополнение исходного патча зависимости вынесено на отдельное согласование.

## Подтверждённая цепочка

1. Первая вкладка получает HTTP429, вторая успешно обновляет ту же сессию и сохраняет новый token.
2. Первая получает TOKEN_REFRESHED через существующий BroadcastChannel. wwPlugin инвалидирует view и вызывает getSession. confirmedSession тоже запрашивает подтверждение SDK.
3. Эти getSession ждут initializePromise. Внутри инициализации ещё идёт прежний `_refreshAccessToken`.
4. Перед следующей попыткой authRecovery видит, что исходный refresh token уже не соответствует сохранённому. Правильно запрещает сетевой запрос, но бросает AuthRetryableFetchError.
5. SDK продолжает exponential backoff: 200, 400, 800, 1600, 3200, 6400, 12800 мс. В сумме примерно 25,4 с. Новых HTTP-запросов на этих семи попытках нет, но стартовая операция не завершается.
6. По истечении retry budget SDK читает актуальную сессию, завершает инициализацию, а UI восстанавливается без reload.

Это **не доказательство бесконечного зависания**. 20-секундный FAIL — подтверждённая длительная задержка. В 40-секундном наблюдении оба браузера восстановились сами.

| Браузер | HTTP ответы вкладок | Успешная вкладка | Задержавшаяся вкладка | Заблокированные старые попытки |
|---|---|---:|---:|---:|
| Chrome | 429 / 200 | 234 мс | 25 651 мс | 7 |
| WebKit | 429 / 200 | 227 мс | 25 643 мс | 7 |

Время относительно загрузки каждого тестового документа; это локальные измерения, не production latency. Обе финальные идентичности — A, оба view — A. Сохранённая сессия не удалялась. Трассы содержат только синтетические идентичности, типы событий, статусы и время.

## Исправлен дефект самого теста

В прежнем harness глобальный count проверялся после await задержки. Оба обработчика иногда видели count=2 и возвращали HTTP200, хотя сценарий назывался two-tabs-error. Две первые трассы показывают именно такой случай: один успешный ответ уже устарел к моменту получения, adapter также превращал его в retryable supersession, и ожидание воспроизводилось без 429.

Теперь номер попытки захватывается до await; первая попытка гарантированно получает 429. Результат true-429-before.log подтверждает по одному 429/200 и ровно два сетевых запроса. Прежние PASS two-tabs-error без зафиксированных статусов нельзя считать доказательством покрытия HTTP429.

## Почему недостаточно правки только UI или типа ошибки adapter

- Событие TOKEN_REFRESHED не потеряно: оно уже получено и обработано. getSession заблокирован ожиданием initializePromise, поэтому дополнительные вызовы/таймеры UI не решают причину.
- В SDK `src/lib/fetch.ts` catch вокруг fetcher превращает любое исключение adapter в AuthRetryableFetchError. Замена бросаемого класса в authRecovery не остановит retry.
- Удалить token fence нельзя: это разрешит отправлять уже заменённый refresh token. Возвращать выдуманный успешный HTTP-response или показывать неподтверждённую сессию нельзя.
- SDK уже имеет AuthRefreshDiscardedError и commit guard. Нужна такая же проверка до повторного запроса, а не новая синхронизация или клиент.

## Минимальное предложение, НЕ ПРИМЕНЕНО

[sdk-retry-supersession.proposed.diff](sdk-retry-supersession.proposed.diff), только исходник GoTrueClient.ts существующей локально исправленной версии 2.119.2:

- Передать в `_refreshAccessToken` уже существующий storedAtStart.
- После backoff, до сетевой попытки сравнить текущее поколение с исходным. При замене/удалении завершить операцию штатным AuthRefreshDiscardedError.
- Не трактовать discard как terminal response сервера: не очищать сессию, не кешировать ошибку против новой сессии. Существующие getSession после завершения инициализации должны подтвердить актуальное состояние обычным SDK-путём.

Эта проверка не делает недействительный token действительным и не отменяет настоящие 400/401. Начальный null snapshot сохраняет штатную возможность внешнего session hydration, пока storage остаётся null. Запись новой сессии по-прежнему защищается прежним commit guard. Проверка до I/O не заменяет commit guard из-за возможной смены состояния после чтения.

Статическая проверка применимости diff к точному исходнику PASS, SHA в proposal-manifest.json. **TypeScript build и execution этого предложения NOT TESTED: исходник не изменялся.** Это не runtime monkey-patch и не новый SDK-клиент.

Следующее действие — разрешить локальное дополнение существующего исходного SDK-патча, собрать отдельный test tarball и выполнить BEFORE/AFTER и согласованную матрицу. Никакой production-установки или изменения CI это не разрешает.

## Воспроизведение

Скопировать tests/auth-session-recovery.browser.mjs в tests отдельного кандидата ca9bb1f с тем же patched SDK. Нужны уже установленные Playwright, Chrome/WebKit. Используются прежние локальные пути fixture, внешняя сеть блокируется.

```sh
MODES=two-tabs-error node tests/auth-session-recovery.browser.mjs
```

Нынешний тест имеет 40-секундный предел для доказательства длительности; его итоговый PASS означает восстановление в этом окне, не устранение 20-секундного дефекта. Для AFTER нужен отдельный жёсткий критерий быстрого восстановления и серия повторов, а не только увеличение timeout.

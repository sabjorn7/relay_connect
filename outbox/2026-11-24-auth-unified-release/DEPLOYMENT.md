# Публикация и откат — только после отдельного разрешения

Этот документ не запускает команды. Сейчас production/main/CI не изменены.

## Перед публикацией

1. Повторно прочитать GitHub main и публичный frontend release marker. Ожидаемая база `e062265304688b744b36b8f2ea021b8270c641ad`. Если они изменились, остановиться и пересверить patch; не перезаписывать новые исправления.
2. Сверить SHA release.diff/rollback.diff из results/summary.json и vendor manifest. Сохранить текущий рабочий SHA и сведения последнего успешного Deploy App. Серверные файлы, БД и секреты этот выпуск не меняет.
3. Подготовить отдельную чистую ветку MeetGuru от подтверждённого base SHA. Применить пакет:

```sh
git apply --check /path/to/package/release.diff
git apply --index /path/to/package/release.diff
git diff --cached --stat
git diff --cached --check -- ':!vendor/auth-js/meetguru.patch'
node --version
npm ci
./node_modules/.bin/vite build -l warn
```

Node должен быть v24.14.0. Контекстные пустые строки внутри вложенного .patch могут давать whitespace warnings; содержимое самого patch сохраняется по manifest SHA. Не исправлять их массовым форматированием.

4. Повторить релевантные тесты из tests. Playwright установлен отдельно; задавать PLAYWRIGHT_MODULE и при необходимости CHROME_EXECUTABLE. Для legacy fixture нужны неизменённый auth-js 2.70.0 и headerAccount из base commit, переданные через LEGACY_AUTH_MODULE/LEGACY_HEADER_MODULE. Не направлять fixture в production API.
5. Проверить состав по changed-files.txt. Не включать посторонние рабочие/неотслеживаемые файлы или dist. После отдельного разрешения создать один conventional commit; сохранить его SHA для отката.

## Штатный Deploy App

1. Только после разрешения опубликовать релизную ветку MeetGuru и открыть PR к main. Предпочесть squash merge, чтобы у выпуска был один однозначный commit для revert.
2. Merge в main автоматически запускает существующий Deploy App. Не добавлять workflow_dispatch и не запускать сторонние deployment scripts. В этом выпуске изменена только Node-версия его существующего build job — 20 → 24.14.0.
3. Дождаться полного успеха обеих фаз assets/HTML. Actions выполняет обычный npm ci и существующие app/landing/postbuild этапы. Они не выполнялись локально в полном production-режиме; отказ pipeline — основание не продолжать ручную публикацию.
4. Read-only smoke после разрешённого релиза: HTML release SHA и доступность JS/CSS, публичные главная/каталог, страницы входа/регистрации, прелоадер. Синтетическая локальная регистрация не заменяет согласованный реальный тест аккаунта; не создавать production-записи или платежи без отдельного разрешения.
5. Для согласованного тестового аккаунта проверить повторный вход, logout и две вкладки. Не проводить настоящее списание. Не менять диагностику, SQL, RLS, backend или инфраструктуру.

## Повторный вход и старые вкладки

Пользователи новой версии начнут с нового auth-v2 namespace и должны войти снова. Старые refresh tokens/cookies не копируются. Старые вкладки могут продолжать работать со своей прежней сессией; обновление страницы переводит их на новый код. Не обещать перенос незавершённого старого PKCE-перехода. Если он не завершился, пользователю нужно начать вход заново.

Сериализация препятствует именно прежнему scanner, не защищает от произвольного same-origin JS. Global logout старой вкладки может законно отзывать серверные сессии того же аккаунта. Не менять эту семантику ради видимости успешного входа.

## Откат

Пакет содержит rollback.diff, который в чистом локальном checkout вернул tracked-файлы точно к base SHA. Это **откат кода**, не тест production-развёртывания и не миграция browser storage.

После отдельного разрешения на rollback:

1. Если выпуск опубликован одним squash commit, создать обычный `git revert <RELEASE_COMMIT_SHA>` в отдельной rollback-ветке от актуального main. Проверить diff. При конфликтах остановиться, не использовать reset/force push.
2. Если main всё ещё точно равен релизному состоянию, альтернативно проверить и применить предоставленный rollback.diff. На изменившийся main не накладывать его вслепую.
3. Проверить сборку на Node/lockfile возвращаемого состояния, затем согласованно merge rollback в main. Это запустит тот же Deploy App и вернёт прежний Node 20 вместе с прежней зависимостью SDK. Дождаться успеха; не копировать dist вручную.
4. Проверить release SHA, публичные страницы и Auth. Ни заказа, ни подписки, ни серверной сессии rollback frontend не удаляет.

**Последствие rollback:** legacy frontend может снова прочитать оставшуюся старую сессию A, даже если в новой версии пользователь вошёл как B. Новый envelope он не импортирует. Поэтому нельзя обещать обязательный повторный вход при обратном переключении или сохранение выбранного аккаунта. На общих устройствах после отката нужно явно проверить аккаунт, выйти и войти в нужный; при неприемлемости этого поведения требуется отдельно согласованный forward-fix вместо возврата к legacy. Автоматической очистки пользовательского browser storage в данном выпуске нет.

Новый namespace/envelope не удалять массово на сервере или через неподготовленный клиентский скрипт. Повторный выпуск снова использует его по штатным правилам SDK, включая срок действия и server revocation. Риск обратного переключения должен быть принят владельцем до команды rollback.

# Отдельный серверный пакет — требуется согласование

## Подтверждённый контекст доступа (только чтение)

В прочитанной схеме `club_chat` и `club_posts` доступны anon и не имеют включённой RLS; buckets club/chat публичные. `club_subs` также не является защищённым источником членства: RLS выключена, есть прямые клиентские операции. Наличие записи в этой таблице само по себе недостаточно для безопасного включения новых закрытых файлов.

Не меняем эти объекты автоматически. Существующие публичные файлы не становятся закрытыми от добавления нового bucket. Их перенос/ограничение — отдельное решение; новые закрытые файлы никогда не направляем туда.

## Точный путь события

1. AFTER INSERT существующей club_chat для неудалённого сообщения → event=club_message, message_id.
2. club_posts INSERT с date_send IS NULL либо UPDATE date_send non-NULL → NULL → event=club_post, post_id. Редактирование опубликованного текста/лайк не создаёт событие. Старые посты не переотправляются.
3. `club_push_dispatch(event, object_id)` unique резервирует одну постановку в очередь. Существующий pg_net отправляет ID в существующую web-push-send с существующим push_send_key. Это не новый сервис. SQL catch не мешает сохранению сообщения.
4. В web-push-send новый dispatcher требует `PUSH_CLUB_ENABLED=true`, иначе пропускает. Старые события/secret header/VAPID/delivery concurrency остаются прежними.
5. Функция читает из БД только принадлежность/состояние объекта, проверяет отправителя и выбирает получателей. Контент, фото, названия клуба и имена не входят в payload.
6. Получатели сохраняют фактический предикат старых push_targets_club_*: active=true AND (end_date IS NULL OR end_date >= current_date), без отправителя, с send_notif и существующим allowlist. Владелец не добавляется автоматически, если не попадает в этот список. Это исправляет предположение старого пакета о владельце и get_club_bundle.subers.
7. Payload: «МитГуру» / «Новое сообщение в клубе» или «Новый пост в клубе»; data.url=/club/?club=ID. Сам ID клуба присутствует для перехода, но закрытого текста нет. Автооткрытие вкладки чата не заявлено. Существующие пользовательские настройки/send_notif сохраняются.

Дедупликация обеспечивает одну постановку на объект, не exactly-once доставку push. Ошибки HTTP после принятия pg_net не повторяются этим пакетом. Старый Expo workflow не меняется; для пользователей обоих клиентов возможны два разных канала уведомлений. Retention служебного ledger и orphan-upload cleanup в этот функциональный diff не включены; это ограничения эксплуатации, а не разрешение удаления данных.

## SQL/Storage предложение

Добавляет attachment metadata в существующую club_chat, private bucket, ограниченные RPC, краткие signed URLs, уникальный request ID и выключенные feature flags. Нет новых messages/chats, новых подписок, изменения цены или оплаты. Restrictive Storage policies предназначены не допустить обход новым bucket через старые широкие политики; прежние buckets этим guard не запрещаются.

Все флаги по умолчанию false. Capabilities требуют одновременно security_reviewed и RLS на chat/posts/subs; сама проверка relrowsecurity не доказывает корректность политик, поэтому security_reviewed выставляется только после ручной проверки.

## Конкретные условия, пока блокирующие установку/включение

1. Согласовать правило доступа к закрытому контенту для end_date=NULL и последнего оплаченного дня. Draft access повторяет latest user_sub (владелец либо последняя запись без end_date/с будущей датой). Это отличается от legacy push recipient predicate; нельзя менять бизнес-правило молча.
2. Защитить источник club_subs от самовольного назначения членства, сохранив существующие легитимные owner/admin операции. В этом пакете нет изменения подписок или их политики.
3. До применения RLS сопоставить реальные existing policies и прямые операции likes/comments/moderation. Draft owner-write club_posts пока не покрывает их совместимость; включать его на production нельзя. Старые permissive политики также могут расширить разрешения — проверить перед применением.
4. Сверить фактическую установленную web-push-send с repo-базой; наличие исходника не доказывает равенство production.
5. Проверить реальную запись голосового в Safari и действующий Storage API на согласованном стенде.

Таким образом PROPOSED.sql — проверяемый локальный security draft для согласования, а не install script. На реальных объектах ничего не применялось. Антивирусная проверка файлов не добавлялась; имя/расширение/MIME не доказывают безопасность содержимого.

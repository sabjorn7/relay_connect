# MeetGuru: существующий антифрод-мониторинг

Дата проверки: 27.11.2026. Только чтение. Никаких платежей, выводов, тестовых callback, изменений production или настроек не выполнялось.

## Вывод

На платформе подтверждены финансовый учёт, проверки корректности выдачи доступа, периодический контроль «оплата без доступа», административное согласование выводов и журнал ряда финансовых действий. Это полезная основа, но **не полноценный поведенческий антифрод**. Нельзя заявлять платёжной системе, что MeetGuru уже выявляет повторные оплаты по карте/BIN/IP, несколько карт одного покупателя, VPN, массовую регистрацию по устройству или аномальные обороты.

Отсутствие найденных правил не доказывает отсутствие любых внешних банковских проверок. Настройки антифрода мерчанта у Prodamus/банков и их фактические срабатывания недоступны.

- Официальная документация Prodamus использовалась для значения полей и границ ответственности, не как доказательство настроек конкретного мерчанта.

Ограничения: `auth.audit_log_entries` возвращает permission denied; действующие Auth rate-limit/CAPTCHA settings не прочитаны. Edge Functions details API для checkout-pay-link возвращает null — это ограничение инвентаризации, а не доказательство отсутствия функции. Полное соответствие всех файлов Edge production репозиторию в этом аудите не установлено. Приватные внутренние таблицы не выгружались; используются доступные определения вызывающих RPC. Часть старых сценариев/ветвей без подходящих сохранённых запусков отмечена отдельно.

Статусы: **РАБОТАЕТ** — есть production-доказательство исполнения/использования; **ЧАСТИЧНО** — данные или часть контроля есть, запрошенного автоматического выявления нет; **ОТСУТСТВУЕТ** — в проверенных доступных источниках реализации не найдено; **НЕ ПОДТВЕРЖДЕНО** — доступа/доказательств недостаточно. «ОТСУТСТВУЕТ» относится к площадке в пределах описанного покрытия, не к банку.

## Что действительно работает

### PaymentGuard — эксплуатационный мониторинг

Активный workflow `Er9qmggzerGKjHGQ` запускается каждые 10 минут. Запуск `47864` от 27.11.2026 08:10:57 UTC завершён успешно; просмотренные десять последовательных запусков подтверждают расписание.

View `payment_guard_tier1` считает за 90 минут оплаченные **неподписочные** заказы по `order.created_at` и свежие платные `user_course` по created_at/updated_at. `anomaly = paid_orders_90m >= 1 AND fresh_paid_grants_90m = 0`. При true граф направляет результат в email-уведомление.

Это не контроль злоупотреблений: одна успешная выдача доступа может скрыть отсутствие доступа по другим заказам; клубные подписки исключены; дата создания заказа не равна времени оплаты. В просмотренном последнем запуске email-нода не выполнялась. Уведомление/доставку искусственно не провоцировали.

### Подтверждение платежа и повторная обработка

BuyCourse: CheckPaid → IF_AlreadyPaid → duplicate audit либо VerifySignRPC → VerifyAmount → AuditWarn → дальнейшая обработка. AuditWarn записывает `mode=warn`; сама эта ветка не останавливается на отрицательной проверке.

Однако текущая production `fulfill_paid_course_order` требует payment_audit с `event=ok`, `sig_valid=true`, `payment_status=success`, `verify.ok=true` перед платной выдачей; исключение нулевой покупки отдельно связано с серверным нулевым заказом. Есть блокировки и receipt для повторного вызова. Подтверждено 86 receipts, все 86 связаны с указанным успешным proof. Просмотренные исполнения BuyCourse 25 ноября дошли до FulfillAllAccesses успешно. Поэтому было бы неверно как заявить «warn вообще не защищён», так и распространить эту защиту автоматически на любые другие платёжные ветки.

В установленном графе Subscription есть проверка HMAC, merchant/status/demo/currency/amount и RPC `club_claim_callback`: соответствие order/owner/club/subscription/profile/amount/currency, locks, защита повторов. Production определение RPC подтверждено; просмотренные сохранённые исполнения подписок относятся к времени **до** обновления графа 23 ноября 19:57 UTC. End-to-end исполнение новой ветки на реальном платеже в этом аудите НЕ ПОДТВЕРЖДЕНО. Защита платежа не считается обнаружением подозрительного поведения.

### Выводы и реквизиты

`request_withdrawal` получает auth.uid(), проверяет положительную сумму, наличие реквизитов и достаточный баланс под блокировкой; создаёт запрос со snapshot. `admin_approve_withdrawal_v2`/`admin_reject_withdrawal_v2` требуют роль администратора, обрабатывают только pending-состояние и пишут admin_money_log. Это согласование, не автоматическое перечисление в банк и не доказательство проведённой KYC-проверки.

`save_my_requisites` проверяет тип получателя и формат/длины реквизитов. Проверки принадлежности банковского счёта человеку, совпадения счетов разных аккаунтов и риска смены реквизитов не найдены. `type_changed_at` отражает смену типа получателя, а не каждую смену банковского счёта. Snapshot сохраняет реквизиты заявки, но не полную историю всех правок профиля.

Обезличенные агрегаты на момент чтения: 2358 заказов, 1028 paid, 1027 с payment_id, 355 с непустым logs; payment_audit — 113 записей (111 ok, 2 duplicate); admin_money_log — 6 (2 approve, 2 reject, 2 commission_change); withdrawal_requests — 14 (8 подтверждено, 6 отклонено). Нельзя считать все старые согласования покрытыми шестью записями admin audit.

## Какие данные доступны для антифрода

| Данные | Наблюдение |
|---|---|
| Внутренний account/order ID, сумма, дата создания и paid | Есть в production; пригодны для агрегатов по аккаунту. Нужна отдельная нормализованная дата подтверждения оплаты для точных временных правил. |
| Provider transaction ID, status, payment_type, sum, currency, attempt | Есть в структурах просмотренных реальных callback. payment_type — категория способа оплаты, не уникальная карта. |
| subscription.id, profile_id, даты и счётчики подписки | Есть в subscription callback. profile_id — профиль подписчика Prodamus, не доказанный fingerprint карты. |
| BIN / маска карты / card fingerprint / уникальный payment-method token | В просмотренных payload и доступной прикладной схеме не найдены. Возможность отдельного API/экспорта — НЕ ПОДТВЕРЖДЕНО; нужен ответ провайдера. Не выводить BIN из неизвестного ID. |
| IP покупателя | В nginx предусмотрен remote_addr. В callback есть x-real-ip отправителя webhook; это не подтверждённый IP покупателя. Связь IP↔покупатель↔платёж не установлена. |
| Email/телефон покупателя | Названия полей присутствуют в callback; значения для аудита не извлекались. Это не банковские реквизиты и не device ID. |
| Даты регистрации, история продаж/выводов | Доступны для будущего сравнения, существующего детектора не найдено. |
| Реквизиты получателя выплат и snapshot | Есть; можно использовать защищённое сравнение без копирования реквизитов в алерты. Принадлежность/дубликаты автоматически не проверяются. |
| IP/устройство Auth | auth logs недоступны. Сбор/срок хранения/возможность связки не подтверждены. |

Полные PAN/CVV не запрашивались. Нельзя утверждать по этому аудиту, что ни один исторический сырой лог никогда не содержал лишних полей: тела старых логов намеренно не выгружались. В отчёт/репозиторий не включены персональные данные, реквизиты, ключи и исходные workflow с credentials.

Все изменения схемы/настроек/правил требуют отдельного одобрения. Порядок: наблюдение → проверка ложных срабатываний → ручная очередь → отдельно согласованные ограничительные меры. Самостоятельных изменений не выполнялось.

## Провайдер и площадка

Провайдер/эквайер может проверять карту, эмитента, 3-D Secure, velocity по карте/BIN/IP на своей форме и возвращать риск/отказы; фактический набор и включение для MeetGuru нужно подтвердить договором и настройками. Не заявляем, что Prodamus уже выполняет весь этот перечень для мерчанта.

Площадка должна связать подтверждённый платёж с аккаунтом/товаром, отслеживать поведение аккаунта и выплаты, вести очередь решений, обеспечивать подлинность callback и идемпотентность. Банковский антифрод не знает полной истории регистрации, курсов и смены реквизитов площадки.

Официальные источники: [параметры и проверка подписи Prodamus](https://help.prodamus.ru/payform/integracii/rest-api/instrukcii-dlya-samostoyatelnaya-integracii-servisov), [параметры подписочных уведомлений](https://help.prodamus.ru/payform/integracii/tekhnicheskaya-dokumentaciya-po-avtoplatezham/uvedomleniya). Документация определяет profile_id как профиль подписавшегося; не даёт оснований приравнивать его к карте. Конкретные поля callback дополнительно подтверждены схемами сохранённых executions.

Готовые формулировки для платёжной системы — PAYMENT-PROVIDER-REPLY.md. Они не отправлялись внешнему адресату.

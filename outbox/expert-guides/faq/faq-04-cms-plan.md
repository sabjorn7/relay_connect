# FAQ CMS + страница инструкций — план (на ревью, ничего не применено)

> Продолжение `faq-02-edit-and-structure.md`. Здесь — конкретный план правок фронтенда и порядок
> выкладки. Миграция БД — отдельными файлами: `2026-10-30_pending_faq_table.sql` +
> `…_rollback.sql` (в корне outbox). Текст вопросов/ответов — из `faq-03-draft.md`, подставляется
> **после** того как владелец ответит на помеченные «?» пункты; этот план не зависит от текста.

## а) Миграция (ссылка)

См. `2026-10-30_pending_faq_table.sql`. Коротко: таблица `public.faq` (audience, category, lang,
question, answer, sort, published, updated_at + id/created_at), RLS: чтение — всем при
`published=true`, запись — только пользователям с `role='admin'` или `superadmin=true` (тот же
admin-чек, что у `admin_approve_course`/`admin_create_promo`); `service_role` ничего отдельно не
выдаётся — он и так обходит RLS. Чистая добавка, ничего существующего не трогает.

## б) Правка `src/_front/views/FaqPage.vue`

Текущее состояние (для справки): весь контент — захардкоженный объект `CONTENT` по `ru`/`en`,
`lang` — локальный `ref`, аккордеон на `<details>`, в конце — блок «Поддержка» с контактами и
ссылками на `/politica`/`/oferta`/`/soglasie` (не трогаем).

**Новое поведение:**
1. При маунте — запрос в `public.faq` через общий Supabase-клиент (тот же паттерн, что в
   `streams/cohosts.js`/`StreamsPage.vue`: `supabase.from('faq').select(...).eq('lang', lang.value)
   .order('sort')`), без фильтра по `published` (его обеспечивает RLS-политика
   `faq_select_published`, а не клиентский код).
2. **Если запрос вернул 0 строк ИЛИ упал с ошибкой** (сеть, таблицы ещё нет после отката,
   RLS и т.п.) — показываем **прежний хардкоженный `CONTENT`** для текущего `lang`, без ошибки
   на экране. Это единственное условие отката — специально сделано так, чтобы пустая таблица
   (ещё не наполненная) и откат миграции были неотличимы от «старого доброго FAQ» для
   пользователя.
3. **Вкладки «Ученикам» / «Экспертам»** — новый `audience` ref (`'students' | 'experts'`,
   по умолчанию `'students'`); переключение — те же кнопки-пилюли, что и `fq-lang`, визуально
   рядом с заголовком. Запрос в п.1 дополняется `.eq('audience', audience.value)`.
4. **Группировка по `category`** — строки из БД группируются на клиенте по полю `category` в
   секции, повторяя текущую вёрстку `<section class="fq-section">`. Порядок секций: по списку
   категорий из `faq-02-edit-and-structure.md` (жёстко зашитый в компоненте массив — 7 категорий
   «Ученикам», 6 «Экспертам»), категории вне списка — в конец по алфавиту. Так не нужно отдельное
   поле sort для самих секций — его несёт список категорий в коде, а `sort` в таблице упорядочивает
   вопросы **внутри** категории.
5. **Поиск** — текстовое поле над секциями, клиентский фильтр по уже загрученным строкам
   (`question`+`answer`, регистронезависимо, без доп. запроса к БД — датасет маленький). При
   поиске категории без совпадений скрываются целиком.
6. **Переключатель РУС/ENG** — остаётся как есть (та же кнопочная пара `fq-lang`), просто теперь
   меняет и `lang` для фолбэк-контента, и фильтр запроса к `faq`.
7. **Рендер `answer`** — сейчас `v-html="item.a"` на доверенном хардкоде. Раз текст теперь может
   редактироваться через Supabase Studio (см. вариант B в `faq-02`), перед `v-html` добавляем
   ленивый `DOMPurify.sanitize(answer, { ALLOWED_TAGS: ['a','strong','em','b','i','br'] })` —
   тот же защитный паттерн, что уже есть у конспекта курса (`cheatsheet`), только `a` здесь
   **разрешён** (ссылки на `/oferta`/`/vozvrat` в тексте нужны), в отличие от конспекта, где `a`
   запрещён. Это решение — на подтверждение дев-ревью, не применено молча.
8. Новая строка со ссылкой **«Подробные инструкции по разделам →»** на `/faq/guides` (см. в).

Итог: `FaqPage.vue` остаётся тем же файлом, добавляются: загрузка данных, `audience`-таб, поиск,
фолбэк-ветка, DOMPurify на `answer`. Верстка/CSS-классы аккордеона и блок «Поддержка» — без
изменений.

## г) Порядок выкладки, окно, откат

**Порядок:**
1. **Сначала миграция** (`2026-10-30_pending_faq_table.sql`) — отдельный деплой БД, ничего не
   ломает (таблица пустая, никто её ещё не читает). Можно катить в любое время, проверить руками
   через Supabase Studio (вставить тестовую строку с `published=true`, убедиться что `anon` видит
   её через `select`, а `authenticated`-не-админ не может вставить/обновить).
2. **Потом фронтенд** (FaqPage.vue + FaqGuidesPage.vue + 3 ссылки «Как это сделать?») —
   обычный пуш в `main` → CI (`deploy-app.yml`) пересобирает и рассинкает весь `dist/`. Фронтенд
   безопасно катить даже с пустой таблицей `faq` — сработает фолбэк на старый `CONTENT`, видимых
   изменений для пользователя не будет, пока владелец не опубликует первые строки.
3. Наполнение текстом (`faq-03-draft.md` после правок владельца) — через Supabase Studio или
   будущую admin-форму, отдельно от деплоя, в любое время после шага 2.

**Окно деплоя:** т.к. деплой — это полная пересборка `dist/` + rsync с `--delete` на
`app.meetgu.ru` (см. CLAUDE.md), любой пуш в `main` может дать активным вкладкам баннер
«обновилась версия» **на всём сайте**, не только на `/faq`. Поэтому:
  - **вне активных эфиров** — проверить `/streams` на отсутствие `status=live` записей перед
    пушем (баннер обновления посреди чьего-то эфира — плохой опыт и для зрителей, и для
    владельца/со-ведущих в LiveKit-комнате);
  - **вне оплат** — не катить сразу после рассылки/рекламной кампании (всплеск чекаутов на
    Prodamus) и не катить в момент, когда идёт вебхук-обработка платежа (короткое окно, но
    безопаснее просто выбрать тихий час, например ночь по МСК).
  - Это чек-лист для того, кто жмёт deploy, а не автоматическая проверка — у меня нет доступа к
    live-метрикам трафика, чтобы подтвердить окно самому.

**Откат:**
  - Фронтенд: обычный `git revert` коммита фронтенд-правок → новый пуш в `main` → CI передеплоит.
    На БД не влияет.
  - БД: `2026-10-30_pending_faq_table_rollback.sql` — дропает таблицу целиком. Безопасно
    выполнять **независимо** от состояния фронтенда в любую сторону — `FaqPage.vue` ловит любую
    ошибку чтения (включая «таблицы нет») и показывает старый `CONTENT`, так что порядок
    отката (сначала БД или сначала фронт) не важен для живого сайта.
  - ⚠️ Если к моменту отката в `faq` уже есть реальные опубликованные вопросы (не тестовые) —
    снять дамп (`select * from public.faq`) до отката, `_rollback.sql` безвозвратно их удаляет.

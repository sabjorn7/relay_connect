## Результат

Три независимых доли автора: **Курсы**, **Клуб**, **Трансляции**. Остаток принадлежит платформе; отдельный новый платформенный баланс не вводится.
Миграция копирует `users.authorCommission` во все три новых поля для каждого существующего пользователя.
Пользователь, который позже станет автором, также имеет правильные исходные значения.
Существующий процент мероприятий остаётся в прежнем `users.authorCommission`. Этот столбец и его административная RPC не меняются.

Новые поля: `authorCommissionCourses`, `authorCommissionClub`, `authorCommissionStreams`.
Диапазон 0..100, без подмены нулевого процента значением по умолчанию.
Триггер INSERT инициализирует новые поля значением старого процента; клиентская регистрация не требует изменений.
Прямые INSERT/UPDATE новых финансовых полей закрыты; администратор меняет выбранное поле через RPC с причиной и аудитом.
Миграция отказывается работать при неожиданных широких INSERT/UPDATE-правах users или несовпадении fingerprint действующих финансовых функций.

## Классификация продаж

- Обычный курс: Курсы.
- Основная платная подложка, связанная через `streams.backing_course_id`: Трансляции.
- Самостоятельная покупка записи, включая курс из `streams.recording_course`: Курсы.
- Выдача записи вместе с эфиром не является второй продажей и не создаёт второе начисление.
- Связанные мероприятия и прежние курсы с `Category='Мероприятия'`, даже без строки events: **старый процент и прежняя формула**.
- Клуб и каждое автопродление: актуальная клубная ставка при обработке подтверждённого платежа.

Классификация/ставка определяются сервером по курсу и связям, не полем product_type из браузера.
Существующее округление BuyCourse `(price * percent / 100).toFixed(2)` сохранено.
Сроки, промокоды, shop/order, проверка суммы и подписи, доступы и старые receipts не переписываются.

## Финансовые обработчики

**BuyCourse:** добавлен один service-only read RPC `get_order_author_shares` перед BuildAllAccesses.
Он возвращает один объект с полным массивом rates. Остальные all-item массивы остаются полными.
BuildAllAccesses выбирает серверную ставку по каждой позиции/автору; FulfillAllAccesses сохраняет прежние credentials и вызов.
SQL повторно проверяет ставку под блокировками. Новые receipts сохраняют ставку/категорию; прежние receipts не обновляются.
Проверка stale-плана по-прежнему завершает транзакцию ошибкой без частичных записей, как текущая проверка старого процента.
Совместимость существующей service-only нулевой оплаты сохранена; её бизнес-правила не меняются.

**subscription:** в production шесть Code-узлов используют фиксированный множитель 0.82.
У единственного текущего клуба старый процент владельца 82%, поэтому первичный перенос не меняет его условия.
Три денежные цепочки заменяются service-only RPC `settle_club_author_share`; старые непосредственные записи баланса/продаж отключаются.
Остальные узлы webhook, проверки payment_status, регистрации, сроков, автосписания и изменения заказа остаются прежними.
RPC проверяет paid/subscription/order/payment_id/сумму/покупателя и связь club_subs→club; автор и ставка читаются из БД.
Продажа, прибавление баланса и receipt выполняются одной транзакцией. Повторный/параллельный callback не начисляет повторно.
Разные платежи одного автора сериализуются по его строке, без перезаписи устаревшим балансом.

Сохранены ДВЕ прежние клубные операции округления: `Number((amount*(rate/100)).toFixed(2))` для sales
и `Number((amount*(rate/100)+oldBalance).toFixed(2))` для баланса. Их нельзя незаметно заменить суммой уже округлённой продажи.
SQL-helper воспроизводит binary64/toFixed через точную целочисленную дробь; проверен сравнением с реальным JavaScript.
Receipt отдельно фиксирует сумму продажи и фактическое изменение баланса. Это сохраняет прежние правила даже для старого баланса с долями копейки.

Исторические оплаченные клубные заказы отмечаются в новой закрытой таблице как historical **без изменения старых данных и без повторного начисления**.
Отметка — защита от повторного callback, а не доказательство правильной обработки исторической продажи.

## Безопасность и ограничения

Секретов, production exports, credentials, pinned execution data, покупателей и реальных платёжных данных в пакете нет.
Механизм checkout, ссылки Prodamus и frontend оплаты не менялись. Корзина не переделывается.
Клубная RPC атомарна только для финансового участка; существующие изменения order/club_subs выше по графу не переносятся.
Нынешний onReceived webhook и его гарантии доставки не меняются. Идемпотентность не означает гарантированную доставку callback.
Существующая проверка клубного webhook не заменяется: усиление проверки подлинности отдельно не реализуется этой задачей.

**Перед production нужен согласованный cutover клуба:** снимок исторических paid-заказов должен соответствовать завершению старых финансовых цепочек.
Если старое выполнение начислит после снимка, новая таблица не узнает об этом автоматически.
Поэтому нельзя вслепую применять SQL и горячо менять workflow при незавершённых старых callback.
Нужны остановка/удержание именно клубного входящего потока на согласованное окно, завершение принятых выполнений,
применение SQL, переключение и сверка платежей окна. Механизм удержания не разрабатывался и production не менялся.
Если владелец выберет переключение без удержания, остаточный риск и ручная сверка должны быть явно согласованы отдельно.

Готово к независимому review. Production GO пока не выдан: нужны review, отдельное разрешение и согласованный cutover.

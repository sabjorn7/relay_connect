# Внедрение и откат — НЕ ВЫПОЛНЕНО

Никаких production SQL, Edge deploy, n8n изменений, commit/push/deploy в ходе разработки.

## Перед выпуском

1. В отдельной релизной копии от актуального main перенести только файлы этой задачи. Исключить Splash/FHD и другие незавершённые изменения. Повторить unit, PostgreSQL/PostgREST, browser и прямой Vite build без postbuild.
2. Владелец сохраняет защищённую резервную копию затрагиваемых определений/ACL/RLS и данных. Не включать её в review. Миграция проверяет md5 текущей fulfill_paid_course_order; несовпадение останавливает её до изменений. Не обходить эту проверку без сравнения.
3. Согласовать короткое окно переключения покупки: SQL закрывает старые прямые записи checkout, поэтому старые открытые вкладки должны обновиться. Просмотр существующих покупок сохраняется. Не объявлять атомарным развёртывание трёх разных компонентов.

## Порядок после отдельного разрешения

1. Владелец вручную применяет `supabase/migrations/pending_unified_checkout.sql` через SQL Editor. SQL выполняется транзакционно; при ошибке STOP. SQL не пишет исторические покупки и не переобрабатывает платежи.
2. Обновить PostgREST schema cache: `NOTIFY pgrst, 'reload schema';`. Выполнить `verify_unified_checkout.sql`. Проверить owner JWT против RPC, отказ anon/foreign, service-only RPC. При несовпадении STOP.
3. Опубликовать только новую Edge Function checkout-pay-link. Она использует серверные SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, SITE_ORIGIN=https://app.meetgu.ru. Не помещать service key в Vite env/браузер/логи; использовать существующее защищённое окружение функций. Проверить JWT и CORS. Другие функции не публиковать.
4. Выпустить frontend от актуального main по штатному Deploy App. Не менять BuyCourse: его проверка платежа/все course_positions/финансовая RPC сохраняются. Не менять Prodamus callback URL.
5. Обновить вкладку; проверить курс, event full/deposit, stream, смешанную корзину, promo preview, owner-only pending orders. Реальный контрольный платёж и его повтор согласуются отдельно. Сверять user_course, все event_registrations, sales, receipt, авторские суммы и отсутствие дублей; HTTP200 или возврат с payform недостаточны.

## Безопасная остановка

`rollback_unified_checkout.sql` — не разрушительный stop новых оформлений. Он отзывает authenticated EXECUTE для cart_add_product и checkout_prepare. Не открывает старые небезопасные DML, не удаляет ledger/продажи/доступы, сохраняет callback/receipt и продолжение уже созданных оплат. Не откатывать старую financial RPC после появления новых заказов: потеряются product hooks/zero semantics. Не запускать старые callback.

При сбое Edge/frontend оставить серверную обработку принятых заказов, закрыть новые оформления, восстановить UI только совместимой версией. Возврат к старому клиентскому checkout потребует отдельной проверки ACL и не является безопасным автоматическим rollback. Возобновление — после исправления вернуть EXECUTE этих двух функций authenticated. Данные не удалять. SQL rollback также применяется только владельцем после разрешения.

## Оставшиеся ограничения

- Реальный Prodamus, уведомления действующего BuyCourse и production RLS не тестировались операциями записи.
- Проверка promo usage_limit сохраняет существующую семантику used_count; неоплаченные ссылки не резервируют активации. Строгая квота скидок при нескольких ранее выданных ссылках не гарантируется, это не новая функция этой задачи.
- Service-role legacy stream-pay-link остаётся отдельно существующим endpoint; новый UI его не вызывает, его прямые клиентские записи закрыты правами новой схемы. Перед выпуском проверить отказ обхода на согласованном стенде, не production-покупкой.
- Проверки цен усиливают серверную границу: несовместимый старый checkout должен предложить обновить страницу, а не fallback к прямым INSERT.
- Полный финансовый rollback после уже завершённых платежей запрещён; существующие возвраты остаются отдельным процессом.

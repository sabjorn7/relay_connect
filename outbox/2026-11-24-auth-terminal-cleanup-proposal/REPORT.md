# MeetGuru: terminal cleanup race

Дата: 24.11.2026. Статус: **предложение, ожидает согласования изменения зависимости**.

## Что подтверждено

Запрос npm registry `npm view @supabase/auth-js version dist-tags --json` вернул latest `2.119.2`; next — `3.0.0-next.29`, canary — `2.119.0-canary.6`, beta — `2.112.0-beta.0`, rc — `2.100.0-rc.0`. Предрелизные теги не считаются совместимым стабильным исправлением и не устанавливались.

Последний стабильный пакет 2.119.2 воспроизводит FAIL для400/401. Проверенный доступный [upstream master](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/src/GoTrueClient.ts) тоже содержит `storedNow → expires_at → _removeSession()` без условного удаления исходного refresh token. Подходящий исправленный официальный релиз не найден. Это не утверждение о проверке каждой исторической версии или закрытых upstream-веток.

В закреплённом исходнике `src/GoTrueClient.ts` участок около5195–5206 читает A через async helper. До последующего удаления другая вкладка может записать B. `_removeSession()` не получает identity исходной операции и удаляет текущий слот. Дополнительный обычный `getItem()` лишь переносит окно гонки.

Повторно выполнен исходный `auth-terminal-commit-gap.mjs`: для400/401 finalUser=null, SIGNED_OUT=1, exit1. Это детерминированная запись B между шагами реального SDK, не воспроизведение узкого окна браузерным планировщиком и не измерение частоты в production.

Повторно выполнен `auth-original-adapter-compat.mjs`: неизменённый старый адаптер на новом SDK после proactive400/401 и входа B блокирует настоящий logout — finalUser=B, AuthRetryableFetchError. Поэтому старый persistent removal guard не возвращён.

## Выбранный вариант для ревью

Патч одного файла исходников auth-js2.119.2. Не применён к кандидату, dependency installation или production.

1. Terminal cleanup передаёт исходный `refreshToken` в условное удаление. Проверка актуального токена и срока access token выполняется внутри критической секции записи. Несовпадение означает отсутствие удаления и нового SIGNED_OUT. Исходная серверная ошибка остаётся результатом refresh.
2. `_saveSession` и `_removeSession` используют один отдельный lock с ключом storage. HTTP-запросы не выполняются под этим lock. Обычный login не ограничивается токеном прежнего пользователя; refresh commit сверяет snapshot и не перезаписывает новую сессию.
3. Прямые записи слота при legacy user hydration также включены в эту секцию. Убран безусловный post-save undo, который мог удалить новую запись; вместо него проверка перед commit под lock.
4. SIGNED_OUT начинает отправляться при сериализованной записи, но Promise подписчиков ожидается после освобождения lock. Иначе callback, выполняющий новый login, создал бы deadlock. Для init-очереди добавлена проверка отсутствия новой сессии перед отложенным SIGNED_OUT.
5. Terminal refresh A не очищает PKCE незавершённого входа B. Явный logout сохраняет очистку PKCE. Это необходимое изменение lifecycle, которое требует регрессионных OAuth-тестов, а не самостоятельная новая функция.
6. Нативный Web Locks вызывается без `steal`. Существующий SDK helper navigatorLock может принудительно отобрать lock по таймауту и позволить старому holder продолжить работу — для атомарной записи такой путь неприемлем. Таймаут 5 секунд только отменяет ожидание; не запускает тело без lock. Это новый предел для короткой storage-секции, не сокращение сетевого/Auth-таймаута.

Проверки terminal token не превращают недействительную сессию в действующую. При ошибке локальной координации исходная terminal ошибка возвращается; запись может сохраниться, но не должна считаться подтверждённой UI. Для этого сохраняются проверки срока и текущей сессии в предыдущем кандидате.

Это минимальный предлагаемый объём для согласованной записи, а не доказанно минимальное решение для всех backend/storage SDK. Правка одного `if` без участия writers не обеспечивает требование.

## Ограничения и риски

- Гарантия сериализации относится к обновлённым вкладкам одного origin, storageKey и partition. Старая вкладка или произвольный raw localStorage writer не участвует в lock. Смешанная работа версий остаётся ограничением rollout; перед объявлением результата требуется тест старой/новой вкладки. Нельзя обещать исправление уже открытого старого JavaScript.
- В браузере без Web Locks предложение намеренно не делает небезопасный process-local fallback: операции записи завершаются ошибкой. Это ограничение поддержки, включая logout, поэтому такие устройства — блокер релиза без отдельного решения. Инициализация и гостевые страницы также требуют проверки при этом отказе.
- В Node используется существующий processLock, который покрывает один процесс. Distributed SSR storage не входит в проверяемую конфигурацию и не получает межпроцессной гарантии.
- Ожидание lock ограничено; зависание/заморозка владельца, закрытие вкладки, недоступный storage и ошибка PKCE cleanup должны проверяться отдельно в целевой матрице. Подписчики не должны ожидаться внутри lock.
- Успешный refresh, explicit logout, login и queued init notifications меняют очередность microtasks. Поэтому старые браузерные PASS не переносятся на этот patch автоматически.
- Не изменяются GoTrue, RLS, SQL, backend, HTTP или платёжная логика. Серверное подтверждение доступа обязательно как прежде.

## Node в CI

Текущий Deploy App использует Node20. Пакет auth-js2.119.2 объявляет Node>=22. Игнорировать engines или переписывать engines пакета не предлагается.

Предпочтительный согласуемый вариант: [однострочный diff](ci-node24.proposed.diff) на Node24.14.0, совпадающий с доступной локальной версией, на которой прежний кандидат собирался. Workflow не менялся и не запускался. После согласования необходимы npm ci и полная CI-сборка; локальный PASS не доказывает её результат.

Альтернативы: дождаться подходящего официального исправления и проверить его требования Node либо отдельно рассмотреть backport на старую SDK-ветку с Node20. Backport 2.70.0 здесь не подготовлен: он должен закрыть также прежнюю двойную очистку и не является меньшим проверенным diff.

## Проверка после отдельного согласования

1. Экспортировать чистую копию исходников закреплённого SDK в отдельный каталог вне установленного node_modules. Проверить SHA из manifest. Применить diff только к этой копии, собрать воспроизводимый локальный пакет с отдельным version suffix и контрольной суммой. Не публиковать его в npm автоматически.
2. Подключить собранный пакет только к новому локальному checkout кандидата9980fa1. Не перезаписывать прежний стенд или lockfile рабочего проекта. Автоматический postinstall, который незаметно меняет node_modules, не добавлять.
3. Первым gate прогнать исходный gap400/401; вариант с настоящим SDK login B; обновление токена того же A; настоящий logout B; поздний SIGNED_OUT; reentrant login из subscriber и queued init. Старый адаптер остаётся отрицательным тестом; заменяющий адаптер должен пройти аналогичный proactive400/401→loginB→logout.
4. Добавить управляемое чередование через две настоящие страницы с Web Locks, включая отсутствие steal, таймаут, старый writer, закрытие/заморозку вкладки. Ожидаемые ограничения не превращать в PASS.
5. Только после gate — существующие Chrome/WebKit recovery, email/VK/регистрация, checkout, PWA где доступна; typecheck SDK, сборка приложения. Внешняя сеть перехвачена, никаких production-аккаунтов или оплат.
6. Отдельно согласовать CI diff и повторить сборку. До всех проверок и следующего разрешения никакого Deploy App.

## Откат и готовность

Сейчас откат не нужен: ни исходник установленного SDK, ни CI, ни production не изменены. Для будущего локального испытания сохранить исходный lockfile и pristine tarball. Откатить локальный тестовый пакет можно новым чистым checkout исходного кандидата и npm ci; не смешивать старую dependency с новым адаптером.

Будущий production-откат должен возвращать единым набором SDK pin/lockfile, Auth-адаптер и потребителей событий к последнему реально опубликованному release SHA, сохранённому перед релизом. Не откатывать только SDK: старые гонки вернутся, а сочетание компонентов может быть непроверенным.

ИТОГ: точное предложение готово к согласованию локального применения и тестирования. Устранение гонки на patched runtime ещё НЕ доказано; к публикации не готово. Нет новых исследований за пределами Auth cleanup и необходимой совместимости Node.

**BLOCKED, не для production и не для упаковки релиза.** Два первоначальных FAIL исправлены в узких воспроизводимых сценариях, но ключ хранения не изолирует существующие потребители интерфейса. По условию пользователя работа остановлена после подтверждения оставшегося критического риска.

SDK собран CJS/ESM TypeScript-компилятором прежней среды. Локальный tarball установлен npm, не ручным редактированием node_modules. После обнаружения пересчёта транзитивных зависимостей при первой установке восстановлен исходный lockfile с изменением только auth-js; затем npm ci установил прежние 375 пакетов. Браузерные проверки AFTER выполнялись после этого восстановления. Проверка отличий lockfile и SHA в results/manifest.json. ## Конкретный оставшийся блокер

В `src/_front/chrome/headerAccount.js`:

- `readStoredSession()` (строки 24–35) сканирует все localStorage keys, не привязан к экземпляру SDK. В тесте новая подтверждённая SDK-сессия B, helper возвращает прежнего A.
- `authCookieUser()` (строки 42–53) читает общую старую sb-access-token cookie. Новый storageKey это не меняет; cookie-изоляция ещё не реализована и не подтверждена тестом.
- `clearStoredSession()` (строки 159–167) удаляет все записи с access_token/refresh_token независимо от ключа. В тесте после вызова существующего signOutUser новая запись тоже исчезает. Для сознательного global logout очистка нескольких сессий сама по себе не является ошибкой; однако это доказывает отсутствие полной изоляции именем ключа.
- `signOutUser()` выбирает токен для серверного logout через тот же сканер. Нельзя утверждать, что отзывается именно выбранный текущим SDK пользователь.

Нельзя выпускать вариант, в котором разные части UI расходятся по идентичности. Не доказано раскрытие серверных данных или обход RLS; подтверждена неверная идентичность в helper, используемом интерфейсом. Старые вкладки с неизменённым helper продолжат сканировать любые обычные записи с токенами; правка helper только нового bundle этого не отменит.

## Минимальный следующий шаг для согласования

Точечно перевести identity-readers и cookie-потребителей нового приложения на подтверждённую сессию единственного SDK/его точный namespace; отказаться от чтения старой общей cookie как идентичности. Это необходимое дополнение к миграции, а не изменение checkout или серверных правил.

Отдельно определить допустимое поведение старых вкладок: их явный global logout может по штатной серверной семантике отозвать новые сессии того же аккаунта. Это нельзя отменить переименованием ключа без изменения смысла global logout. Для старого произвольного localStorage scanner обычный JSON под новым ключом также остаётся видимым. Нужен согласованный переход, который исключает использование старым UI новых токенов; не добавлялся новый формат/носитель хранения или механизм синхронизации без проверки. Простое требование закрыть вкладки не даёт технической гарантии для всей аудитории.

## Что остаётся NOT TESTED

- UI-logout при offline/500/зависшем отзыве, немедленное скрытие персональных компонентов в реальном AppHeader. PASS выше относится к SDK logout с успешным синтетическим ответом. Старый fire-and-forget wrapper пока может не донести ошибку SDK до UI.
- Refresh без Web Locks: запрет установлен в коде до сети, отдельные негативные browser cases ещё не запускались; неподдерживаемый браузер не получает обход write lock для входа. UX такого отказа не завершён.
- Миграция cookies, VK callback, реальный server global logout, физический PWA.
- Повтор полной critical/email/VK/checkout матрицы, чистая Vite-сборка кандидата: остановлены после сохраняющегося FAIL. Предыдущие PASS не перенесены на этот кандидат.
- `scope=others`, исключение из SIGNED_OUT subscriber, ошибка localStorage, закрытие всего процесса/сон ОС.

## Последствия и откат

Новый ключ требует повторного входа всех пользователей. Старые refresh tokens не импортируются, старые серверные сессии не удаляются миграцией. Незавершённый старый PKCE flow нельзя считать автоматически совместимым с новым namespace. Эти последствия пока не готовы к выпуску из-за legacy readers.

Откат production не нужен: ничего не установлено. Для локального возврата использовать прежний отдельный кандидат 03e44e2. Не применять эти incremental diff к основной ветке. Упаковка и согласование публикации возможны только после устранения identity-reader FAIL и повторных регрессий.

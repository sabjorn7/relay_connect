## Сохраняющийся блокер старой вкладки

Новый JSON под другим ключом остаётся видим старому scanner, который ищет строки access_token и refresh_token во всех записях. Исправление новой версии не меняет уже загруженный старый JS. Его logout может выбрать новый token B и удалить оба namespace. Это подтверждено отдельной старой вкладкой; не устранено текущим патчем.

**Минимальный вариант для отдельного согласования:** в существующем storage adapter использовать версионированную сериализацию, которую прежний scanner не распознаёт, например UTF-8 JSON, помещённый в base64-поле envelope. Без миграции старых токенов и без новой синхронизации. Это именно новый формат хранения, поэтому здесь НЕ реализован. Это совместимость с legacy scanner, не шифрование и не защита от произвольного JS того же origin. Проверить обратимое кодирование, CAS/epoch guards и обновление вкладок. Простое вложение исходного JSON не подходит: строки access_token/refresh_token останутся в записи.

Также нельзя продолжать выдавать новые токены через старые общие sb-access-token/sb-refresh-token cookies: старый UI читает их независимо от storage. Потребуется согласовать версионирование или прекращение этих cookie после проверки непосредственно зависимых потребителей. В текущем кандидате plugin всё ещё пишет прежние cookies; новая функция их игнорирует, старый JS — нет. Изменение cookie-контракта не внедрено.

## Global logout старой вкладки

Даже после изоляции локального формата штатный подтверждённый global logout старого аккаунта может отозвать серверные сессии того же аккаунта, включая новую. Это ожидаемая семантика global logout, не terminal cleanup race. Локальная изоляция не должна обещать сохранение сессии после намеренного global logout того же пользователя. При разных A/B старый интерфейс не должен получать B token через scanner/cookie. Нужны обе границы выше. Реальные серверные отзывы не выполнялись, результат подтверждён только синтетическими запросами; SQL/RLS не менялись.

## Повторный вход, внедрение и откат

Новый auth-v2 namespace по-прежнему требует повторного входа пользователей. Старые refresh tokens не переносятся; серверные сессии не изменяются миграцией. При будущей изоляции формата старый PKCE/cookie flow требует проверки. **К закреплению SDK и чистой релизной сборке пока не готово.**

Следующий шаг — отдельное согласование адаптера сериализации и cookie-границы, затем исправление оставшегося FAIL и повтор полной регрессии. Новых механизмов без согласования не добавлено. Для локального отката использовать исходный отдельный кандидат b720606; production-откат не нужен, публикации не было.

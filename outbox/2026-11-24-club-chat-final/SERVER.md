# Минимальная серверная часть, только для согласования

## Вложения

Существующий bucket club/chat публичный, поэтому для новых закрытых вложений он не подходит. Предлагается один private bucket `club-chat-private`; никакие старые объекты/права bucket не изменяются.

Путь: club_id / SDK user ID / request UUID.ext. RPC берёт автора только из auth.uid(), проверяет доступ через read-only helper, наличие storage.objects и размер, пишет metadata в прежнюю club_chat. Уникальный request ID и transaction advisory lock обеспечивают повторную попытку без второго сообщения. SQL разрешает изображения/документы/аудио в границах существующего validateFile. Содержимое файла антивирусом не проверяется.

Storage INSERT/SELECT ограничены только новым bucket, UPDATE/DELETE запрещены в нём. Restrictive guards защищают новый bucket от старых широких permissive Storage policies, не переопределяя старые buckets. Чтение через signed URL на 60 секунд; уже выданная ссылка живёт до истечения даже после logout.

Capability RPC по умолчанию false. Нет новой таблицы настроек. Узкий read-only access helper повторяет ранее использованную интерпретацию latest user_sub: владелец либо последняя запись без end_date/с будущей end_date. Он не пишет в членство и не меняет существующую логику клуба; правило доступа нового bucket входит в отдельное согласование SQL. Никакая миграция членства не предлагается.

## Push

1. BEFORE INSERT club_chat (не deleted) → ID нового сообщения. UPDATE сообщения только сохраняет старую отметку, не рассылает.
2. BEFORE INSERT опубликованного club_posts (date_send IS NULL), либо UPDATE date_send non-NULL→NULL → ID поста.
3. web_push_queued_at в самой существующей строке фиксирует принятие pg_net. Клиентское значение/reset игнорируется trigger. Повторное редактирование/перепубликация не ставит уведомление заново. Новая таблица дедупликации не нужна.
4. pg_net после commit вызывает существующую web-push-send с существующим x-push-key. Ключ не хранится в пакете.
5. Edge проверяет прежний ключ, PUSH_CLUB_ENABLED, опубликованность/неудалённость записи, источник клуба/отправителя; выбирает подписчиков по фактическому legacy push predicate active=true и end_date NULL либо >= current_date. Исключает отправителя, send_notif=false, отсутствующий профиль и пользователей вне существующего allowlist. Владелец получает push только если попадает в существующий список получателей.
6. Existing serviceworker уже принимает title/body/data.url и показывает штатные icon/badge. Код serviceworker не меняется. Открывается /club/?club=ID; автоматический выбор вкладки чата не добавляется.

Триггеры устанавливаются выключенными, Edge gate false по умолчанию. Включать только после согласования и установки обработчика. Нет backfill/рассылки исторических событий. Ошибка enqueue не блокирует сохранение сообщения; лог — фиксированная техническая причина без текста. HTTP failure после постановки pg_net не повторяется этим пакетом; это at-most-once enqueue, а не гарантия доставки. Старый Expo/n8n не меняется, и пользователи двух каналов могут получить оба уведомления.

## Отдельно, без расширения задачи

Из предыдущей read-only проверки известны anon-доступ к club_chat/club_posts, публичность старых вложений и непротектированный источник club_subs. Этот пакет их не исправляет и не утверждает, что существующая модель доступа стала безопасной. RPC/private bucket ограничивают новые операции, но доверяют существующей модели членства. Новые private-вложения не превращают старые публичные фото в закрытые. Эти вопросы отдельно зафиксированы; подготовка UI/push продолжена, широкого SQL доступа нет.

Для выпуска нужны только явное одобрение данного минимального SQL/Storage/Edge состава и тестовый rollout. Не применять старый PROPOSED.sql из 5b56ab2 вместе с этим пакетом.

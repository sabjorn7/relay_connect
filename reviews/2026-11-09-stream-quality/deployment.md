# Порядок внедрения — только после отдельного разрешения

1. Сохранить текущие SQL definitions/schema, orchestrator files и template в защищённом backup. Сверить SHA-256 production-файлов с `production-baseline-sha256.json`. Любой drift требует разбора diff; не копировать старую локальную папку livekit-poc. В meetclone создать отдельный релиз от актуального production HEAD: переносить только изменения качества, не текущий dirty tree целиком.
2. Владелец вручную применяет `pending_stream_video_quality.sql`, затем `NOTIFY pgrst, 'reload schema';`. Это additive DDL, старым записям HD, Full HD disabled; существующие RLS/уведомления не переписываются. Проверить default/check, deny anon/authenticated для start RPC и внутренних таблиц; capabilities доступна публично, содержит только version/флаг. Функции определения private stream/чатов/уведомлений не меняются.
3. В изолированном стенде применить candidate orchestrator к совпадающей базе. Конфиг/env/SDK не менять. Провести настоящий HD и Full HD тест по `test-plan.md`, подтвердить partial external failure/reconciliation. Не включать production-флаг до результата.
4. Для production обновить только orchestrator src/server.mjs, db.mjs, livekit.mjs и новый videoQuality.mjs после сверки diff. Потребуется перезапуск **только live-orchestrator** в отдельном согласованном окне. Это временно влияет на выдачу/обновление токенов и команды управления. Самостоятельно LiveKit, Egress, Redis, n8n, PeerTube не перезапускать. Уже работающий Egress не перенастраивается этим кодом; всё равно не проводить замену control plane посреди важного эфира.
5. Атомарно заменить template/grid.html согласованным вариантом (в нём только pin SDK). Действующие headless страницы не перезагружать. Новые Egress должны получить новый шаблон; проверить правила кеширования. Не перезапускать LiveKit Egress ради замены HTML.
6. Выпустить изолированный frontend по существующему процессу — только отдельное согласование commit/push/deploy. SQL и API должны быть доступны прежде frontend. Проверить HD, старый live без snapshot, авторизацию владельца/соведущего/администратора, скрытый и платный эфир без тестовой покупки.
7. PeerTube: текущая конфигурация live transcoding enabled, дополнительных разрешений нет. В админке версии 7.0.1 согласовать исходное Full HD и дополнительные 720p/480p. Сначала измерить CPU/память/диск/исходящий трафик на изолированном тесте. Не считать настройки обычных VOD (360/720) настройками live. Не применять новые настройки к действующим эфирам. Нужно отдельно определить, требует ли выбранный механизм изменения конфигурации перезапуска PeerTube; не выполнять его автоматически.
8. После успешного HD/Full HD и нагрузки разрешить Full HD отдельно. Начальный лимит один одновременный эфир; это предохранитель, не гарантия мощности. Пример для владельца (НЕ выполнен):

```sql
UPDATE public.stream_video_quality_settings
SET full_hd_enabled = true, max_full_hd_live = 1
WHERE singleton;
```

9. Новый контрольный эфир только с отдельного согласия: проверить actual capture, outbound stats, active run snapshot, actual Egress encoding, PeerTube HLS variants и decoded 1920×1080 на стороне зрителя. Не объявлять GO по одной строке настроек. При 1080p+multi-variant профиле повторить одновременно с обычным HD, измерить влияние на него.

## Откат

Первый безопасный шаг — `pending_stream_video_quality_rollback.sql`: выключает новые Full HD, не удаляет настройки/историю, не изменяет текущий Egress или камеру. Текущий новый код остаётся: владельцы могут выбрать HD для следующего запуска, работающие Full HD сохраняют snapshot. Нельзя обнулять quality активных run или останавливать их скриптом.

Технический откат frontend/orchestrator — только в отдельном окне без активных Full HD. Старый backend не понимает snapshots; возвращать его при работающих Full HD небезопасно для новых подключений. Предварительно согласовать будущие предпочтения Full HD: иначе guard закономерно отвергнет старт от старого hard-coded HD writer. Предпочтителен operational rollback флагом и fix-forward.

Объекты SQL не удалять: старые клиенты их игнорируют. Не удалять run history и не менять исходные streams/права/оплаты. Настройки PeerTube откатывать сохранённым конфигом только после отдельного решения; удаление вариантов из текущего live не выполнять.

## Нагрузка и границы

1080p = 2,25× пикселей 720p. Egress video bitrate 3 → 4,5 Мбит/с = +50%; камеры Full HD дополнительно передают simulcast layers. При p2p=0 каждые 100 зрителей на 4,5 Мбит/с дают примерно 450 Мбит/с video payload до накладных расходов. Дополнительные HLS encodes нагружают PeerTube независимо от SFU. Разовый idle snapshot хоста не заменяет нагрузочный тест; заполненный swap требует внимания администратора до релиза.

# Изолированные медиа-испытания — подготовка 2026-11-09

## Решение

**BLOCKED для выполнения медиа-испытаний; NO-GO для включения Full HD в production.**
Изучены README.md, deployment.md, test-plan.md, SQL-миграция, candidate livekit.mjs/videoQuality.mjs и локальный PoC. Исходники приложения и production не изменялись. Миграции, комнаты, Egress и эфиры не запускались. Старые unit/fixture результаты не считаются медиа-измерениями и повторно не запускались.

На текущем Mac (Darwin arm64) найдены ffmpeg/ffprobe. docker, podman, colima, livekit-server, livekit-egress отсутствуют в PATH. В livekit-poc/selfhost есть Compose-заготовки с Redis, LiveKit, Egress и Node, но не отдельный полный PeerTube-стенд; образы LiveKit/Egress используют latest. README старого PoC предлагает существующий PeerTube и LiveKit Cloud — это не подтверждённо изолированное окружение. Новых инструментов и инфраструктуры не установлено.

Отдельная комната на существующем LiveKit не изолирует CPU/RAM/сеть Egress и PeerTube. Синтетический/unlisted эфир на общем сервере также создаёт нагрузку на реальные эфиры. Поэтому такой способ здесь не используется. Доступный отдельный Linux-хост не предоставлен; это не утверждение об отсутствии любых серверов у владельца.

## Минимальный отдельный стенд

Требуется согласовать отдельный временный Linux x86_64-хост, не production. Начальная инженерная оценка для HD и Full HD одновременно: 16 выделенных vCPU, 32 GiB RAM, 100 GiB SSD, порт 1 Gbit/s. Это бюджет испытаний, не обещанная ёмкость. Дополнительные зрители/транскодирование могут потребовать больше. Для одиночных последовательных прогонов допустим меньший стенд после оценки ограничений, но он не закроет проверку параллельной нагрузки.

LiveKit рекомендует каждому Egress минимум 4 CPU / 4 GB, Room Composite может занимать несколько CPU: https://docs.livekit.io/transport/self-hosting/egress/. Для двух композиций предусмотреть два отдельных Egress worker, каждый не менее этого бюджета, и отдельный резерв для PeerTube транскодирования, SFU и служебных процессов.

Состав:

- Изолированные LiveKit, Redis для LiveKit/Egress, два Egress worker.
- Отдельный PeerTube 7.0.1 с собственными PostgreSQL, Redis и media storage; не production-аккаунт.
- Candidate orchestrator от production-baseline, неизменённые совместимые SDK-зависимости, candidate grid.html. SDK шаблона хранить локально для независимости от CDN.
- Локальный PostgreSQL/PostgREST с синтетическими users/streams/auth и проверенной миграцией качества; production Supabase недоступен. Обвязка авторизации только тестовая, роли и стартовый контракт сохраняются.
- Изолированная сборка настоящих StreamCallPage/StreamViewer с тестовыми endpoints, фиктивными учётными данными; никаких production env.
- Тестовый HTTPS с доверенным сертификатом, LiveKit WSS/ICE/TURN при необходимости. Доступ только согласованным тестовым устройствам через отдельную сеть/VPN; DNS production не менять.
- Read-only сборщик метрик хоста/контейнеров, ffprobe и локальные артефакты. Не передавать Docker socket приложению/orchestrator.

Образы зафиксировать по версиям и digest после сверки с production-baseline, не запускать latest из старого Compose вслепую. Установка зависимостей может использовать сеть отдельно от испытаний. В runtime разрешены только адреса стенда и тестовых устройств; блокировать остальные исходящие TCP/UDP, включая production. Сохранить необходимый ICE/RTCP и HLS внутри разрешённой сети — `--network none` не подходит для проверки реальной камеры на отдельном устройстве.

Перед запуском: проверить резолвинг всех тестовых endpoints, отсутствие production secrets/общих volumes, блокировку production HTTP/WSS/UDP, отсутствие внешних webhook/push/платежей/email. Не копировать существующие .env. Новые тестовые credentials, сертификаты, хост и сетевые правила требуют отдельного согласования. Создание стенда в этом задании не выполнено.

## Порядок прогонов и измерения

1. Зафиксировать версии, digest, SHA кандидата, настройки и квоты. Применить SQL только в тестовой БД, включить Full HD только там. Снять idle baseline 5 минут для каждого сервиса.
2. По отдельности HD и Full HD: прогрев 2 минуты, затем 10 минут измерений. Сначала синтетическая движущаяся таблица с мелким текстом и таймкодом, затем реальная камера 1080p30. Синтетический источник не подтверждает совместимость физической камеры.
3. Capture: getSettings; outbound RTP каждого simulcast-слоя: frameWidth/frameHeight, framesPerSecond, bytesSent и временные дельты, qualityLimitationReason. Для потерь/RTT — remote-inbound RTP и корректная связь localId/remoteId. Недоступные метрики оставлять null.
4. В шаблоне Egress тестовой копии собрать размеры декодируемых входных video и inbound WebRTC stats. На выходе Egress измерить поток до PeerTube пассивной локальной записью/зеркалом RTMP на стенде; проверить, что зеркало не меняет encoding. ffprobe: codec, width/height, timestamps/frame count и FPS. Битрейт считать по bytes/duration на репрезентативном интервале; target bitrate не равен actual.
5. PeerTube: начать с live-конфигурации, эквивалентной production, затем отдельно включить тестовую лестницу 1080/720/480. Сохранить только обезличенные поля master/variant manifest (без URL с секретами), измерить сегменты ffprobe и decoded videoWidth/videoHeight/FPS в тестовом браузере. Проверить Embed getResolutions/setResolution и Auto, переключение без повторного старта, буферизацию/dropped frames. Если cross-origin API не предоставляет decoded stats, измерять внутри отдельного тестового PeerTube-плеера, не обходить origin в приложении.
6. Каждые 2–5 секунд: CPU (с указанием нормировки по ядрам), RAM RSS/working set, CPU throttling, OOM, swap, bytes RX/TX, дисковый I/O/заполнение. Разделить Egress→PeerTube и PeerTube→зритель. Не суммировать host/veth counters как независимый трафик. Метрики снимка не заменяют p95 и пик за прогон.
7. HD + Full HD одновременно 15 минут, затем 2 и 4 ведущих с разными источниками, экран/PDF. Сравнить HD с одиночным baseline. 1080p композиции не гарантирует 1080p каждой маленькой плитки.
8. Ограничить только uplink тестового отправителя: 8 → 5 → 2 Мбит/с, затем отдельно RTT +100 ms и loss 1%, 3% (ступени по 3 минуты). Вводить tc/netem в выделенном namespace, не на общем интерфейсе production и не на канале управления. Проверить адаптацию, предупреждения, отсутствие разрыва и восстановление после снятия ограничений.
9. Проверить утрату ответа create/commit/stop только тестового Egress: reservation не освобождается при неопределённом результате; вручную сопоставить room/egress/run без дублей. Токены и RTMP URL в артефакты не включать.
10. Safari на согласованном Mac/iPhone: реальная камера, fallback, звук/видео, возврат из фона, переключение HLS; screen share только там, где реально поддерживается. Headless Chrome/WebKit не объявлять тестом Safari или UVC.

Формат строки измерений: run_id, UTC timestamp, stage, requested_profile, measured_width/height/FPS, bytes_delta, interval, bitrate, loss/RTT, CPU/RAM/network, evidence_file. Никаких SDP, ICE, IP участников, access tokens, RTMP keys и production данных.

## Предлагаемые критерии допуска (согласовать до прогона)

- Подтверждено 1920×1080 на capture, основном outbound, Egress output и decoded HLS у зрителя для Full HD; аналогично 1280×720 для HD. Для движущегося тестового источника устойчивые 25–30 FPS после прогрева; статический PDF не оценивать по требованию 30 FPS.
- Измеренный bitrate представлен как распределение, а не требование постоянно достигать target: статичная сцена и VBR закономерно ниже.
- Нет OOM, аварий Egress, устойчивого swap/throttling, потери контроля старта/остановки; плановый запас CPU не менее 20% на измеренной конфигурации. Это предварительный бюджет, а не универсальная гарантия.
- В нормальной сети после прогрева нет ребуферизации/разрывов в 10-минутном прогоне; при добавлении Full HD обычный HD не получает новых остановок и снижения фактического разрешения. Зафиксировать dropped frames, latency и отличие от baseline.
- Слабая сеть может снижать качество; это не дефект само по себе. Требуются предупреждение/метрики, работоспособность и восстановление, а не гарантированные 1080p при 2 Мбит/с.
- PeerTube предлагает только реальные варианты; Auto и ручное переключение проверены на фактическом потоке. Нагрузку лестницы оценить отдельно от исходного единственного варианта.

## Безопасное развёртывание после успешных испытаний

Следовать deployment.md: защищённые backups и сверка SHA → отдельное разрешение → additive SQL владельцем и schema reload с Full HD выключенным → candidate orchestrator/template в согласованном окне → изолированный frontend-релиз → контрольный HD → разрешённые настройки live-транскодирования PeerTube → отдельное включение Full HD с лимитом один → контрольный Full HD. Старые/работающие эфиры не перенастраивать. Испытания на более мощном хосте не доказывают производительность production: перед включением нужен сопоставимый ресурсный бюджет или отдельно разрешённый production canary с лимитом и наблюдением.

Первый откат — запрет новых Full HD флагом из существующего rollback SQL, только с разрешения. Текущие run/snapshot и медиапотоки сохранить. Технический возврат backend/frontend только без активных Full HD, по deployment.md; историю/доступы/эфиры не удалять.

Следующий необходимый шаг владельца: предоставить/согласовать отдельный Linux-хост и установку перечисленного тестового стека, его сетевой доступ и тестовые устройства. До этого создание тестовых комнат на production и заявление об измеренном 1080p недопустимы.

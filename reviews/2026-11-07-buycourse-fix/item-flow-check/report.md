# BuyCourse: проверка передачи items в n8n 1.90.2

Проверен единственный вопрос к пакету `db2ed0129965bb9fa0a9c3e75ed7b525c91817b8`. Production не вызывался и не изменялся. Финансовый SQL, workflow JSON и helpers исправления не изменены.

## Вывод

В подготовленном графе нет потери items на цепочке `Code → GetPositions → GetCourse → UsersCreater → UsersBuyer → BuildAllAccesses`. При заказе из четырёх разных курсов количество выходных items: **4 → 4 → 4 → 4 → 4 → 1**, причём единственный итоговый item содержит `plan` из всех четырёх оплаченных позиций. Минимальное исправление не требуется.

## На чём основан вывод

Проверены официальные исходники тега `n8n@1.90.2`. Их Git blob SHA и SHA-256 сохранены в `source-manifest.json`.

1. [Code.node.ts](https://github.com/n8n-io/n8n/blob/n8n%401.90.2/packages/nodes-base/nodes/Code/Code.node.ts): `mode` по умолчанию — `runOnceForAllItems`. Dispatcher возвращает весь массив, полученный из Code. Исходный Code получает один заказ и возвращает по item на `course_positions`; BuildAllAccesses явно работает в all-items режиме и возвращает один полный план.
2. [Supabase.node.ts](https://github.com/n8n-io/n8n/blob/n8n%401.90.2/packages/nodes-base/nodes/Supabase/Supabase.node.ts): операция `get` проходит `for (let i = 0; i < items.length; i++)`, вычисляет фильтры для каждого item, добавляет все строки ответа в `returnData` и сохраняет `pairedItem.item=i`. Одинаковый автор/покупатель не приводит к дедупликации items.
3. [WorkflowDataProxy.ts](https://github.com/n8n-io/n8n/blob/n8n%401.90.2/packages/workflow/src/WorkflowDataProxy.ts): `.item` использует paired-item tracing, `.all()` — весь массив `taskData.main[branchIndex]`, независимо от текущего paired item. По умолчанию берётся связанный output и последний сохранённый run узла. **Разные runs не объединяются.**
4. [workflow-execute.ts](https://github.com/n8n-io/n8n/blob/n8n%401.90.2/packages/core/src/execution-engine/workflow-execute.ts): входные items сохраняются массивом; `executeOnce=true` ограничивает вход первым item. На всех шести узлах проверяемой цепочки флаг отсутствует. Перед исполнением входные pairedItem переиндексируются; это воспроизведено в harness.
5. В фактическом review-графе каждый промежуточный узел имеет ровно один вход от предыдущего и один основной выход 0 к следующему. Нет циклов, Merge, SplitInBatches, разделения курсов по ветвям или нескольких входящих путей в эту цепочку. Ветвление проверки оплаты происходит до неё. Каждый callback имеет собственный runData. Поэтому здесь нет ситуации, в которой `.all()` видит только последний фрагмент нескольких запусков.

`UsersBuyer` использует `$('GetPositions').item.json.owner`. Проверен реальный алгоритм WorkflowDataProxy: индекс проходит назад через UsersCreater/GetCourse к соответствующей позиции. Все четыре запроса выбирают покупателя заказа. BuildAllAccesses использует ID-поиск курсов/авторов, а не случайный порядок ответов.

Если lookup возвращает неполные данные, план отвергается до вызова транзакционной RPC: отсутствие позиции/курса не превращается в частичную выдачу. Если промежуточный узел вообще не выдаст items, эта ветка не дойдёт до RPC; это ошибка данных, а не усечение исправного многотоварного заказа.

## Выполненные проверки

**10 PASS, 0 FAIL**, результаты — `results.json`:

- Фактическая топология, all-items режим, отсутствие executeOnce и циклов.
- Один курс.
- Четыре курса, два автора, полный план и 16 read-only lookup-запросов.
- Четыре курса одного автора без потери дублирующихся author items.
- Несколько позиций одного курса.
- Пропавший ответ курса: корректная цепочка pairedItem и отказ неполного плана.
- Пропавшая оплаченная позиция: отказ до settlement.
- `.all()` не ограничен текущим item; последний run по умолчанию, явный `(0, 0)` выбирает первый.
- Выбор связанного output branch и явного branch 0.
- Обращение к невыполненному узлу выдаёт ошибку.

## Границы проверки

Это source-backed изолированный harness, **не запуск полного сервера n8n**. Выполняются исходные классы Supabase, Code dispatcher, WorkflowDataProxy и функции построения фильтров версии 1.90.2. Синтетические ответы БД, ExecuteFunctions context и доступ к структуре графа заданы локально. Результаты нод сохраняются в формате runData. VM2 заменён `node:vm`; task runners отключены в harness. Полный scheduler/HTTP/PostgREST/credentials/UI/import workflow здесь не тестировались. Код scheduler изучен статически; не выдаём это за production E2E.

Node: 24.14.0 (для встроенного `stripTypeScriptTypes`); никаких npm-пакетов не устанавливалось. Скрипт не содержит API-ключей, production URL, реальных покупателей или платежей; он не вызывает финансовую RPC.

## Повторение

В каталоге этого дополнения:

```sh
python3 download-sources.py
node check.mjs
```

Первая команда получает только публичные исходники n8n с raw.githubusercontent.com и проверяет SHA-256/Git blob SHA. Исходники загружаются в локальный `vendor/`, включая upstream LICENSE.md, но не публикуются в relay. Существующие несовпадающие файлы не перезаписываются. Вторая команда полностью локальная: сеть и credentials не используются. По умолчанию она читает workflow из родительского review-пакета; при необходимости путь к корню пакета задаётся первым аргументом.

Финансовая SQL-логика и готовый способ внедрения остаются прежними. Этот конкретный вопрос передачи items закрыт в указанном объёме; новый согласованный контрольный платёж после внедрения остаётся отдельной проверкой настоящего n8n.
